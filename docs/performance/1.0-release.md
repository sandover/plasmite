# Plasmite 1.0 performance measurements

Measured October 1, 2026 on one Apple M5 Pro Mac with 48 GiB RAM, macOS
26.6.2 (25G83), Rust/Cargo 1.88.0 and LLVM 20.1.5, using optimized release builds.
These measurements describe the stated workloads on this host. They do not
establish network performance or performance on other platforms.

## Comparison with 0.8.0

The repository's [benchmark comparison script](../../skills/plasmite-release-manager/scripts/compare_local_benchmarks.sh)
ran three sequential suites per version on the same host, with no concurrent
builds or benchmark jobs. Baseline: `v0.8.0` (`c5f5fdd`). Candidate: final 1.0
storage/notification code in `fd5c858`; later release-note and fixture-only
changes do not change those operations.

Each suite used 5,000 messages per writer in append/multiwriter scenarios;
1 MiB and 64 MiB pools;
approximate payload targets of 128, 1,024 and 16,384 bytes; and 1, 2, 4 or 8
writers. All rows below use **fast durability**. They do not measure synchronous
flush costs. Multiwriter rows include independent writer processes. Append
rows distinguish reused encoded payloads from encoding JSON on every append.

Values are the **median time per message across three runs**, in microseconds.
Lower is faster. Differences are calculated before rounding. Changes are
absolute time differences, not throughput
percentages. For multiwriter rows, suite duration is divided by all appended
messages (5,000 × writer count). The canonical raw output instead divides
by the per-writer count; this report converts those rows to aggregate time
per message. Percentage comparisons within the same writer count are unchanged.
Representative improvements and regressions are both shown.

| Operation | Payload target (B) | Pool | 0.8.0 µs/message | 1.0 µs/message | Change (µs) |
| --- | ---: | --- | ---: | ---: | ---: |
| append | 1,024 | 1 MiB | 13.662 | 11.789 | -1.873 |
| append + JSON encoding | 1,024 | 64 MiB | 15.634 | 14.288 | -1.346 |
| append + JSON encoding | 16,384 | 64 MiB | 27.094 | 26.251 | -0.843 |
| 2 writers | 1,024 | 64 MiB | 17.798 | 10.654 | -7.144 |
| 4 writers | 1,024 | 64 MiB | 17.363 | 7.808 | -9.554 |
| 8 writers | 1,024 | 64 MiB | 17.512 | 10.059 | -7.452 |
| indexed read, middle | 128 | 1 MiB | 0.166 | 0.875 | +0.709 |
| indexed read, middle | 1,024 | 64 MiB | 0.167 | 1.042 | +0.875 |
| scan, near newest | 1,024 | 1 MiB | 14.125 | 20.000 | +5.875 |
| scan, near newest | 1,024 | 64 MiB | 359.958 | 215.500 | -144.458 |
| scan, near newest | 16,384 | 64 MiB | 281.500 | 177.583 | -103.917 |

Across all append lanes, median time per append was 3–14% lower; across all
multiwriter lanes, median time per message was 35–66% lower. These percentages
are reductions in elapsed time per message. Throughput percentage changes are
not numerically interchangeable with them.

Very small indexed reads became slower: the new read path acquires a coherent
shared lock and returns an owned payload snapshot. The canonical lookup lanes
measure lookup time, rather than full JSON decoding or application consumption;
result ownership differs between versions. Some short scans also became slower,
as shown above. Longer scans avoid copying skipped payloads and improved in the
representative 64 MiB cases.

The existing release gate passed unchanged: 15% regression threshold,
0.0001 ms/message noise floor, and 0.2 ms/message minimum blocking baseline for
lookup/scan lanes. Small lookup regressions remain real even though that policy
does not block release on them.

To repeat the canonical comparison from the release checkout:

```bash
bash skills/plasmite-release-manager/scripts/compare_local_benchmarks.sh --base-tag v0.8.0 --runs 3
```

## Consumer work and reader notifications

A separate controlled comparison used the same full JSON decode and checksum
consumer on clean pre-snapshot code (`751e4d1`) and the final 1.0 read path.
The consumer fetched retained sequence 1 and consumed the full decoded blob.
Idle lanes used 100,000 reads for small blobs and 10,000 reads for 64 KiB blobs
per run. See the [consumer benchmark source](consumer-latency.rs); it also
contains raw-payload and metadata lanes not summarized here.
For a 256-byte blob, median idle p50 latency rose from 0.708 to 1.292 µs; for a
64 KiB blob, it rose from 20.791 to 22.417 µs. This includes necessary snapshot
and synchronization costs; copying a borrowed baseline payload alone does not
provide the new coherent-read contract.

Moving optional reader notification outside the append lock was also measured
with the same owned-snapshot contract on both sides. Three runs used 128 MiB
pools seeded with one retained target message. A separate writer thread with
its own pool handle appended a finite burst of 10,000 small messages, retaining
the consumer's target. Consumer
latency includes full JSON decoding, all-byte checksum consumption and timing.
The table reports the median of each run's p50/p95/p99, in microseconds.

| Blob (B) | Notification under lock: p50 / p95 / p99 (µs) | Notification after unlock (1.0): p50 / p95 / p99 (µs) |
| ---: | ---: | ---: |
| 256 | 2.291 / 6,075.208 / 10,277.042 | 1.542 / 4.000 / 10.334 |
| 1,024 | 1.959 / 8,475.000 / 11,522.208 | 1.833 / 3.667 / 9.334 |

These percentiles describe finite writer bursts, not an unlimited-writer
starvation or OS scheduling guarantee. Submicrosecond values are sensitive to
approximately 42 ns clock quantization on this host. Commit and requested flush
still finish before unlocking; notifications are hints, and readers retain
sequence checks and bounded polling.

To reproduce the final-version consumer lanes in a disposable release checkout:

```bash
cp docs/performance/consumer-latency.rs examples/consumer-latency.rs
cargo run --release --example consumer-latency -- .scratch/consumer-latency
```

The output includes per-run percentile samples; repeat three times for medians.
This standalone driver is development tooling. Its comparison with the
pre-snapshot version and in-lock notification variant was a controlled local
experiment, separate from the canonical tagged-release gate.
